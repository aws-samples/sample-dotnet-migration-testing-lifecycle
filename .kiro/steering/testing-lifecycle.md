# Testing Lifecycle — State-Machine Comparison Testing

This document defines the complete testing lifecycle for verifying that a target system behaves identically to a reference system. It uses a state-machine model where pages have states and users perform transitions between them.

**Applies to:** Any two-system comparison (legacy→new migration, version A→B, SQL→PostgreSQL, framework upgrade).

---

## Core Principle: Reference First, Two Human Gates

```
┌───────────────────────────────────────────────────────────────────┐
│  EXECUTION ORDER (NEVER SKIP OR REORDER)                          │
│                                                                   │
│  1. Analyze reference source code -> design modules + plan.json   │
│  2. HUMAN GATE 1: Human signs off the plan                        │
│  3. Write Reference AND Target tests, one author slot per module  │
│     in parallel (Modules/{Page}.Mod{X}/, build-module each)       │
│  4. One run for all modules: read-only modules in parallel,       │
│     mutating ones serialized with a service restart (the runner)  │
│     Reference + Target -> CSS capture -> 4 module reports         │
│     EXCEPTION GATE: Reference baseline failed -> stop and ask     │
│  5. Auto-fix Target, all modules per round, max 2 rounds          │
│  6. Final report generated by the runner (no hand-written text):  │
│     baselines vs Target, fixes, performance, NOT_TESTED, UNRESOLVED│
│  7. HUMAN GATE 2: Human signs off the final report (or "fix X")   │
└───────────────────────────────────────────────────────────────────┘
```

All execution goes through `.\.kiro\test-project\lifecycle.ps1` (the runner). It starts the
apps, builds the shared Harness once and every module project
(`.kiro/test-project/Modules/{Page}.Mod{X}/`), runs Reference and Target for every module,
captures CSS, writes the reports and the chat renders, and is the only writer of
`status.json`, `timings.json`, `PROGRESS.md` and `chat/`.

**Presenting = writing the report + the chat render; never pause.** Presenting a module
report is satisfied by `reports/Module<X>_Parity.md` (and its CSS diff, performance and
manual-test siblings) plus the `module-result` chat render that the run step relays
(`CHAT-RENDER`, see `#lifecycle-chat-display.md`). Never stop to present a module report.

**Parallelism and data isolation.** Each module has its own project and output folder, so
modules build and run side by side. `plan.json modules[].dataEffect` decides the schedule:
`read-only` modules run in one parallel batch (at most `-MaxParallel`, default 4), then each
`mutating` module runs alone and the runner restarts the data service after its Reference
and after its Target run, so every system starts on seed data.

## Phase Overview

| Phase | Name | Purpose | Workflow step | Human gate |
|-------|------|---------|---------------|------------|
| 0 | Analyze | Read source code, define states, modules, plan.json, css-map.json | `plan` | **Gate 1: plan sign-off** |
| 1 | Reference Baseline | Capture source-of-truth values | `author` (6 parallel slots), `run` | Only the **exception**: Reference baseline failed |
| 2 | Target Capture | Same workflow on Target, alongside Reference | `author`, `run` | — |
| 3 | Comparison Reports | Parity + CSS + performance + manual tests (runner-generated) | `run` | — |
| 4 | Fix & Rerun | Auto-fix the Target, all modules per round, max 2 rounds | `auto-fix` | — |
| 5 | Module Complete | Recorded in status.json by the runner | — | — |
| 6 | Final Documentation | `reports/FinalReport.md` generated by `-Action report` | `final-report` | **Gate 2: final report sign-off** |

The human is asked exactly twice (plan, final report). The only other stop is the exception
gate (comparing against a broken Reference baseline is meaningless) or a repeated
environment failure (exit 3), which is a failure stop with the doctor fix text.

### What the chat shows (CHAT-RENDER views)

| When | View | Content |
|------|------|---------|
| Gate 1 | `plan` | Modules table (user story, steps, assertions, data effect, CSS states), a steps table per module (what the user does, fields that change / stay the same with values), states, NOT_TESTED |
| Start of the run step | `tests-authored` | Per module: Reference/Target test names and revision, steps (vs plan), assertion calls, build result and time |
| Each module finishes | `module-result` | Reference and Target step reports with actual values, performance per step, functional gaps, CSS diffs (incl. `layout.*` geometry rows), Reference defects (only when found) |
| Run finishes | `run-summary` | Per module Ref/Target pass counts, findings (H/M/L), CSS diffs, ms; Phase 3 (Run Reference + Target) wall time, harness errors |
| Each fix round | `fix-round` | Per fix: finding, module, kind, file, change, before -> after, rerun result |
| Gate 2 | `final` | Executive summary with phase timings and total lifecycle time, module results, open items |

Every view starts with the phase line (`Phase k of 5 (<name>) - elapsed mm:ss - estimated remaining mm:ss`).

## Phase Checks — Runner-Verified (status.json)

Every check is PASS or FAIL with evidence from a file; the runner computes them, agents read
them with file tools. If a check is FAIL the workflow does not advance by itself: the step
handles it by its exit-code table, and anything still open goes to the final report.

### After Phase 0 (gate 1)

| # | Check | Evidence |
|---|-------|----------|
| 1 | `state-map/states.md`, `transitions.md`, `assertions.md`, `css-capture-plan.md` exist | File paths |
| 2 | `state-map/plan.json` has every module with `userStory`, `dataEffect`, `plannedSteps`, `steps[]` (length = plannedSteps), test names, `cssStates`, `notTested` reasons, plus top-level `states[]` | plan.json `revision`; `render -View plan` shows no WARNING line |
| 3 | `state-map/css-map.json` maps every planned CSS state | Element list per state |
| 4 | Plan signed off | `status.json.plan.signedOff == true`, `plan.signedOffRevision == plan.json.revision` |

### After each module run (`run-page` / `rerun-target`)

| # | Check | Evidence |
|---|-------|----------|
| 1 | Module project built | Console `[build] Module X PASS <ms>ms log=...` (or `[build-module] X PASS ...`), `runs/ModuleX/build.json` |
| 2 | Reference baseline valid | `modules.X.reference.status == "PASS"` (results.json present, not aborted, 0 failed steps/assertions, every planned CSS state captured); else exit 2 = exception gate |
| 3 | Target executed | `modules.X.target.status != "NOT_RUN"` with step/assertion counts |
| 4 | Four reports written | `modules.X.reports.*` (Parity, CSS_Diff, Performance, ManualTests) |
| 5 | Per-step timings for both systems | `timings.json latest.X.Reference/Target.steps[].stepMs` |
| 6 | Open items counted | `modules.X.openFindings` (incl. Target content checks `page.*`), `actionableCssDiffs` (incl. `layout.*` geometry rows), `notTested` |
| 7 | Baseline issues listed, not counted | `modules.X.referenceDefects` (content checks on the Reference: leaked template syntax, console/page errors); never part of the Target verdict |

### Auto-fix loop exit

| # | Check | Evidence |
|---|-------|----------|
| 1 | Clean | `status.json.fixLoop.clean == true` (0 open findings, 0 actionable CSS diffs, every module run, no harness errors) |
| 2 | Or budget used | `fixLoop.round == fixLoop.maxRounds` (2); remaining items are UNRESOLVED in the final report |
| 3 | Every fix recorded | `fixes.json` entry with `kind`, `before`, `after`; `fixLoop.history[]` before/after counts |

### Final report (gate 2)

| # | Check | Evidence |
|---|-------|----------|
| 1 | `reports/FinalReport.md` generated by `-Action report` with the 5 sections per module + final-report sections | Console `[report] reports/FinalReport.md written (N modules)` |
| 2 | Reference baselines shown side by side with Target values | Section in FinalReport.md |
| 3 | UNRESOLVED findings and harness errors listed with evidence | Section in FinalReport.md |
| 4 | Human signed off | `status.json.finalReport.signedOff == true` |

## State-Change Verification — Mandatory Pattern

Every test behavior that modifies state MUST follow:

```
1. CAPTURE BEFORE STATE — record specific field values
2. PERFORM ACTION — the interaction being tested
3. CAPTURE AFTER STATE — same fields as step 1
4. ASSERT — explicit comparison:
   - If value SHOULD change: before ≠ after AND after = expected
   - If value should NOT change: before = after
   - If value should REVERT: after = original (pre-dirty)
5. VERDICT — ALL pass → VERIFIED | ANY fail → FINDING
```

### What NEVER Qualifies as VERIFIED

| Evidence | Why Invalid | What's Required |
|----------|------------|-----------------|
| "Header clicked, no error" | No proof of outcome | Capture row order before AND after |
| "Dialog closed" | Only proves dismissal | Also prove: no data saved, grid unchanged |
| "Save button blinks" | Only proves dirty flag | Also prove: which field changed, from what to what |
| "Page stayed on same URL" | Only proves URL | Also prove: data reverted to pre-edit values |

## Module Design Rules

Each module = one complete user workflow end-to-end.

| Signal | Module boundary needed |
|--------|----------------------|
| User's GOAL changes | New module |
| Requires reset between steps | Sub-flow or new module |
| Outcome is fundamentally different (save vs cancel) | Separate modules |
| Edge case shares same context | Sub-flow within module |
| Requires different credentials/data | Separate module |

### Module Format (Mandatory)

```markdown
## Module X: [Action] → [Outcome]

*"[First-person story: what the user is doing and why]"*

| Step | What the user does | What should happen |
|---|---|---|
| 1 | [action] | [outcome — what changes AND what stays the same] |
| 2 | ... | ... |

**Sub-flow X1: [Edge Case]**
| Step | What the user does | What should happen |
|---|---|---|
| 1 | [action] | [outcome] |
```

## Mandatory Outcome Tests (Every Page)

| # | Scenario | What MUST Be Verified |
|---|----------|----------------------|
| 1 | Save round-trip | Changes persist, success message, UI resets to clean |
| 2 | Cancel round-trip | ALL changes discarded, reverts to server state |
| 3 | Sort verification | Row order demonstrably different (capture full sequence) |
| 4 | Create/Upload | Item appears, count increases, dirty indicator set |
| 5 | Delete | Item removed, count decreases |
| 6 | Dirty state triggers | For each trigger: save indicator changes |
| 7 | Navigation lock | Dirty + navigate → prompt appears |
| 8 | Dialog lifecycle | Open → fill → OK → saved. Open again → fields empty. Cancel → no change. |

## Reference Example: Module Design (Data Entry Page Migration)

> The following shows how modules were designed for a document upload page migration.
> Your modules will differ based on your application's functionality.

**Module A: Page Load & Read-Only Inspection**
*"I opened the page to look at documents — no changes."*

| Step | What the user does | What should happen |
|---|---|---|
| 1 | Opens page with a valid entity | Page shows heading, info section, grid, upload panel |
| 2 | Clicks Save without changes | Message "No records added/updated" — no dialog |
| 3 | Clicks download icon | File downloads, page unchanged |
| 4-8 | Clicks each sort column header | Rows reorder, arrow indicator appears |

**Module B: Make Changes → Cancel (Discard)**
*"I changed things but decided not to save."*

| Step | What the user does | What should happen |
|---|---|---|
| 1 | Starts at clean page | Save indicator clean |
| 2 | Changes a dropdown | Save indicator activates (dirty) |
| 3-4 | Makes additional changes | Still dirty |
| 5 | Clicks Cancel | ALL changes revert, page refreshes from server |

**Module C: Make Changes → Save (Commit)**
*"I changed data and saved it."*

| Step | What the user does | What should happen |
|---|---|---|
| 1 | Makes changes | Save indicator activates |
| 2 | Clicks Save | Confirmation dialog opens |
| 3 | Fills required field, clicks OK | Changes persist, success message, clean state |

## Quality Checks — Expanded (runner-verified, reviewed at the final gate)

These quality rules apply to every module. The runner and the report generator check them
and record the result in `status.json` / `runs/Module<X>/summary.json`; anything that fails
becomes a counted finding or an UNRESOLVED item in `reports/FinalReport.md`. Nobody pauses to
present them; the human reviews them once, at gate 2.

### Plan (Phase 0, before gate 1)

| # | Check | Evidence |
|---|-------|----------|
| 1 | States defined with key indicators | `state-map/states.md` |
| 2 | Modules in workflow table format (story + steps) | `state-map/transitions.md` |
| 3 | Assertions per step (what changes, what stays the same) | `state-map/assertions.md` |
| 4 | **CSS capture plan per state, including transient elements** (dialogs, popups, expanded dropdowns) | `css-capture-plan.md`, `css-map.json` |
| 5 | Control inventory per module | Selector, type, label for every control |
| 6 | NOT_TESTED items with a specific reason | `plan.json modules[].notTested` |

### Reference baseline (Phase 1)

| # | Check | Evidence |
|---|-------|----------|
| 1 | Reference test builds and runs (not crashed / timed out) | `modules.X.reference.status`, `abortReason == null` |
| 2 | **Every PASS has ACTUAL data values** (not "header clicked") | Step Report descriptions in `reports/ModuleX_Parity.md` |
| 3 | CSS captured for ALL planned states, transient elements **while visible** | Baseline rule: a missing planned state = exit 2 |
| 4 | HTML diff safety net: zero uncovered changes | Per-step "0 uncovered diffs" |

### Target capture (Phase 2)

| # | Check | Evidence |
|---|-------|----------|
| 1 | Target test builds and runs | `modules.X.target.status != "NOT_RUN"` |
| 2 | Every Reference assertion mirrored on Target with the same `(step, field, type)`; EQUALS/CONTAINS constants copied verbatim | Unmirrored = counted `test-coverage` / `missingAssertions`; changed constant = `test-expectation` |
| 3 | Every Reference capture mirrored on Target | Missing = `missingCaptures` (counted) |
| 4 | **Every state-change step captures BEFORE + AFTER + explicit comparison** | CHANGES / STAYS SAME assertions in results.json |
| 5 | Every behavior has an outcome: VERIFIED / FINDING / NOT_TESTED (no silent skips) | Counts in the module Summary |
| 6 | Mandatory outcome tests present (Save, Cancel, Sort, Create/Upload, Delete, Dirty, Nav lock, Dialog) where the page has them | Plan modules |

### Reports and fixes (Phases 3-4)

| # | Check | Evidence |
|---|-------|----------|
| 1 | Parity, CSS diff (all planned states), performance and manual-test reports per module | `modules.X.reports.*` |
| 2 | Manual tests have numbered steps a person can follow without context | `reports/ModuleX_ManualTests.md` |
| 3 | Every fix recorded with before -> after; rerun verdict from the runner, never claimed | `fixes.json`, `fixLoop.history`, `results.prev.json` vs `results.json` |
| 4 | No regressions: counts after a fix are the same or better | `fixLoop.history[].modules.X.*Before / *After` |
| 5 | Cross-module isolation: each module runs independently | Own project/output per module; `[schedule]` line (read-only parallel, mutating serialized) and `[apps] restart service (fresh data)` lines; pass counts equal a `-MaxParallel 1` run |

## Cross-Cutting Behavioral Verification Plan (Phase 0)

During Phase 0 analysis, EVERY page must document these 24 behaviors from the reference system. These become mandatory test assertions in later phases.

| # | Behavior | What to Document | Why It Matters |
|---|----------|-----------------|----------------|
| 1 | Default page size | Number of rows shown on first load (e.g., 10) | Pager math depends on this |
| 2 | Default sort column + direction | Which column, ASC or DESC? | First-load row order must match |
| 3 | Clear/Reset resets ALL | Does Clear reset page size, sort, filters, AND pagination? | Partial reset = QA bug |
| 4 | Dialog close behavior | Backdrop click? ESC? Button only? | BackdropClick=false if legacy blocks it |
| 5 | Navigation lock (dirty + navigate → prompt) | Which navigations trigger it? Tab? Menu? Back? | Missing lock = data loss |
| 6 | Navigation lock prompt text | Exact wording of the confirmation message | Must match character-for-character |
| 7 | Empty grid state | What's visible? Headers? Buttons? Just red message? | Common mismatch source |
| 8 | Progress/loading on which operations | Search, paginate, save, export, dialog open? | Missing spinner = UX gap |
| 9 | Success message format | Prefix "Information:"? Color? Auto-dismiss? | "Information: Record(s) added" vs just "Record(s) added" |
| 10 | Error message format | Prefix "Error:"? Color? Persistent or auto-dismiss? | Must match reference exactly |
| 11 | Pagination format | "View X-Y of Z" — with commas? Spaces around dash? | "1,404" vs "1404" is a real gap |
| 12 | Sort icons visible by default? | Always visible, or only on hover? | Visual parity issue |
| 13 | Grid hover color | What color on row hover? Different from background? | CSS comparison catches this |
| 14 | Grid alternating row colors | White/grey pattern? Which colors exactly? | CSS mismatch if wrong |
| 15 | Date inputs — calendar on text click? | Or icon only? Can user type after pick? | Interaction difference |
| 16 | Export filename pattern | Include timestamp? Page name? Format? | "PageName_MM-dd-yyyy.xlsx" |
| 17 | Export columns vs grid columns | Same count? Export usually has MORE columns | #1 source of export bugs |
| 18 | Multi-select "Select All" present? | Does reference have check-all/uncheck-all? | Missing feature if skipped |
| 19 | Dialog button order | OK/Cancel or Cancel/OK? Which is on left? | Visual parity |
| 20 | Add-mode default rows | How many blank rows when "Add" clicked? | Usually 1, sometimes 5 |
| 21 | Buttons visible when grid empty? | Add/Export/Save still showing? Or hidden? | Conditional rendering |
| 22 | Breadcrumb links | Where does each segment navigate to? | Wrong link = navigation bug |
| 23 | Cancel on dialog — what happens to edits? | Discarded? Kept in form? Confirmation? | Data loss if wrong |
| 24 | Save without changes — what message? | "No records added/updated"? Or silent no-op? | UX expectation |

**Usage:** During Phase 0, fill in the "Reference Behavior" for each item. During Phase 2 target testing, assert each matches. Any mismatch = FINDING.

## Autonomous Execution Rules (Anti-Deviation Enforcement)

These rules govern agent behavior during test execution. Violations are blocking failures.

### Auto-Fix Rules (No Human Needed)

| Rule | Behavior | Limit |
|------|----------|-------|
| Selector not found | Fix selector and rerun automatically | Max 3 attempts |
| Timing/wait issue | Increase wait and rerun automatically | Max 3 attempts |
| Build error in test code | Read error, fix, rebuild | Max 3 attempts |
| Environment failure (runner exit 3) | Rerun the same runner command once (the runner does preflight and app start) | Max 2 attempts, then report the doctor `[FAIL]` line |

### Hard Rules (NEVER Violate)

| # | Rule | Consequence of Violation |
|---|------|-------------------------|
| 1 | **NEVER ASK for permission to fix selector/timing errors** — just fix and rerun (max 3) | Wastes human time on mechanical fixes |
| 2 | **NEVER REPORT partial results as complete** — if 3/5 modules done, say "3/5 done" | False completion = trust violation |
| 3 | **NEVER LOOP on same error > 3 times** — record the evidence and continue (it reaches the human in the final report) | Infinite loops waste time |
| 4 | **NEVER skip CSS diff report** — it's mandatory after target completion | Missing CSS = incomplete testing |
| 5 | **Module isolation is non-negotiable** — no shared state between modules | Shared state = unreliable results |
| 6 | **Functional validation mandatory** — no presence-only tests | "Element exists" ≠ "feature works" |
| 7 | **NEVER weaken assertions to make tests pass** | Hiding bugs ≠ fixing bugs |
| 8 | **NEVER stop outside the designed gates** (plan sign-off, final report sign-off, Reference-baseline exception). A failing Target module does not block the next module; its findings go to auto-fix and, if still open after 2 rounds, to the final report as UNRESOLVED | Extra prompts cost the human more time than manual testing |

### Escalation Protocol

When hitting the 3-attempt limit, do not stop. Record the evidence (a `HARNESS-ERROR X: ...`
progress message for harness failures; an UNRESOLVED entry for findings) and continue. The
final report carries it to the human at gate 2 in this form:

```markdown
## UNRESOLVED — [Module X], [Step N]

**Error:** [exact error message]
**Attempts:**
1. [what was tried] → [result]
2. [what was tried] → [result]
3. [what was tried] → [result]

**Root Cause Assessment:** [best theory]
**Question for the human:** [specific question — not "what should I do?"]
```

The only mid-run stop is the Reference-baseline exception gate (and a second exit 3).
