# Reporting Standards

Reference: `#reporting-standards.md`

Mandatory report formats and presentation rules for all lifecycle phases.

---

## After EVERY Reference Module Execution — Present 3 Sections:

In the automated lifecycle this is satisfied by the generated `reports/Module<X>_*.md` and the module-result chat render (CHAT-RENDER); never pause to present.

1. **Step Report** — Table: Step | Status | Description (plain English with DATA values)
2. **HTML Diff Report** — Uncovered gaps per step
3. **Summary** — Assertions count, baseline values captured

## After EVERY Target Module Execution — Present 5 Sections:

In the automated lifecycle this is satisfied by the generated `reports/Module<X>_*.md` and the module-result chat render (CHAT-RENDER); never pause to present.

1. **Step Report** — Table: Step | Status | Description (plain English with DATA values)
2. **Performance Comparison** — Reference ms vs Target ms per step
3. **Functional Gaps** — Reference behavior vs Target behavior differences
4. **CSS Diff Report** — Element-level styling differences
5. **Summary** — Assertions, gaps, CSS diffs, performance

---

## Step Description Rules

Every step description MUST include:
- What action was performed (plain English)
- What DATA changed (with ACTUAL values)
- What stayed the same (if relevant)
- What UI feedback appeared (messages, indicators — actual text)

**BAD:** "Created record, message appeared"
**GOOD:** "Created record 'TEST_Item_165224' (Phone='555-0001', City='Dallas'). Save clicked → message 'Record(s) added successfully'. Form cleared."

---

## PASS/FAIL Rules

1. Default status is FAIL — only upgrade to PASS with verifiable data
2. NEVER mark PASS if ANY assertion failed
3. NEVER mark PASS without showing actual data proving it
4. NEVER assume correct behavior without data verification
5. False positive FAIL is acceptable — false positive PASS is NEVER acceptable

---

## On Failure — Investigation Sequence

### Step A: Selector issue?
1. Check selector registry for known patterns
2. Check if similar tests passed with different selectors
3. Try alternatives based on DOM knowledge

### Step B: Data/configuration issue?
1. Check test data exists
2. Check settings file values
3. Verify form was filled correctly

### Step C: App bug?
1. Read target source code
2. Compare with reference — is behavior intentionally different?
3. If different without justification → FUNCTIONAL GAP

### Step D: Unresolved → present to human:
1. Show what was tried (A-C)
2. Show error/stack trace
3. Show captured data
4. Ask specific question

## Functional Gap Classification

| Severity | Criteria | Example |
|----------|----------|---------|
| HIGH | Different data/behavior | Sort not working, save not persisting |
| MEDIUM | Different messaging | Success prefix present vs missing |
| LOW | Formatting only | Pager "1,404" vs "1404" |

## CSS Diff Report Format

```markdown
| Issue | Element | Property | Reference | Target | Severity | Action |
|-------|---------|----------|-----------|--------|----------|--------|
| The grid row is normal weight on the old page (Reference) and bold on the new page (Target). | GridRow | font-weight | 400 | 700 | HIGH | Fix: set font-weight: 400 |
| Text size of the cell is smaller by 1px on the new page (Target) (13px on the old page (Reference) vs 12px). | Cell | font-size | 13px | 12px | MEDIUM | Align to reference |
```

### Issue column (plain English)

Every CSS table (CSS_Groups.md, Module<X>_CSS_Diff.md, chat module-result and final, FinalReport
md/pdf/docx incl. UNRESOLVED) starts with an **Issue** column: one short sentence a non-developer
understands, generated by `IssueText` from templates + the group's data (never LLM text; stored as
`runs/css_groups.json groups[].issue`, also the fixer's task title). The technical columns stay.

- "old page (Reference)" / "new page (Target)" every time.
- Elements by visible name and a plain role word (`The 'Active' checkbox`, `Buttons (First Page, Next
  Page and 2 more)`), grid cells by their column header (`The Payor Name column cells (first 3 rows)`),
  never role tokens such as `gridcell cells`.
- Colors in words (`black`, `dark gray`, `faded gray`, `light gray`, `white`, `blue`, `pale yellow`, ...;
  `ColorMath.Name`), sizes as `bigger/smaller by N px`, weights as `bold` / `semi-bold` / `normal weight`;
  impact when deterministic (`- harder to read (contrast 1.9:1, below the 4.5:1 minimum)`).
- State clause from the states it was seen in (`while a cell is being edited`); none when it shows in
  every planned state. Singular/plural verbs follow the element count.

Examples:

```markdown
| The Payor Name column cells (first 3 rows) exist on the old page (Reference) but not on the new page (Target) while a cell is being edited. | G6 | 1: gridcell cells, column 2 (first 3 rows) | missing on Target | present | missing | HIGH | C [cell_edit_open] |
| Buttons (First Page, Previous Page, Next Page, Last Page) look different: text is black on the old page (Reference) and faded gray on the new page (Target) - harder to read (contrast 1.9:1, below the 4.5:1 minimum). | G2 | 4: button 'First Page', ... | color | rgb(0, 0, 0) | rgba(0, 0, 0, 0.26) | HIGH | A [page_load] |
| Labels (Code, Payor Name, Status) are bold on the old page (Reference) and normal weight on the new page (Target). | G9 | 3: label 'Code', ... | font-weight | 700 | 400 | HIGH | A, B [all 8 states] |
| At a narrow window (768px) the 'Active' checkbox is partly cut off (clipped by its container) on the new page (Target) when the page first loads; on the old page (Reference) it is fully visible. | G2 | 1: checkbox 'Active' | hidden or clipped at 768px width | fully visible | clipped by its container | HIGH | A [page_load] |
| The old page (Reference) has a large empty gap (508.5px) between the last grid row and the pager; the new page (Target) has 13.5px when the page first loads. This is an old-page defect; do not copy it. | G3 | 1: Grid pager | gap between last row and pager | 508.5px | 13.5px | HIGH | A [page_load] |
```

### Purpose line and plain values (every generated report)

- Every report section that holds a table gets a one-line purpose sentence above it (what the table
  shows, which side is old/new, units); columns name their units (`Old page (Reference) ms`).
- Recorded values are shown in plain words in chat and documents (`asc` -> `ascending`, `none` ->
  `not sorted`, `true` on `.enabled` -> `enabled`, `(not asserted)` -> `not checked on the new page`);
  the audit md keeps the raw value in brackets.
- Module-result and the final Executive Summary end with a `What this means: ... What to do: ...` line
  (deterministic from the counts).

Severity:
- **HIGH**: Visually noticeable (bold vs normal, wrong color)
- **MEDIUM**: Size/spacing differences above the `VisualChecks.Severity` px thresholds (padding, > 1px font)
- **LOW**: No visual impact (font-family fallbacks, equivalent values, <= 1px size, deltaE < 3, weight 500 vs 600)

Style/state rows are recalibrated by `VisualChecks.Severity` (method: `css-comparison-methodology.md`,
"Severity recalibration"); the audit `runs/css_rows_all.md` shows the rule per row.

### Theme groups (actionable = groups)

CSS rows are grouped per page (`reports/CSS_Groups.md`, `runs/css_groups.json`). `Module<X>_CSS_Diff.md`
and `CSS_Groups.md` start with ONE group table, then the individual (element-specific) findings in the
table format above, then accepted groups; every raw row stays in `runs/css_rows_all.json` / `.md` with
its group id.

```markdown
| Issue | Group | Elements | Property | Reference | Target | Severity | Seen in | Action |
|-------|-------|----------|----------|-----------|--------|----------|---------|--------|
| Corner rounding of buttons (Add, Save, Undo and 43 more) is bigger by 1px on the new page (Target) (3px on the old page (Reference) vs 4px). | G3 | 46: button 'Add', button 'Save', button 'Undo', ... | border-radius | 3px | 4px | MEDIUM | A, B, C [page_load, sorted] | Buttons: border-radius 4px -> 3px, 46 elements: change one CSS rule / theme token in the Target (...) |
```

- Seen in lists the modules and states; `[all 8 states]` when the group shows in every planned state,
  more than 4 states as `first 3 and N more` (full list: `runs/css_groups.json`).
- Border sides: border-top/right/bottom/left rows of one element with identical values are ONE group
  with property `border` (all four) or `border (top, bottom)`; sides with other values stay separate.
- State fold: a `hover.` / `focus.` / `disabled.` row whose values equal the base-state row of the same
  element and property joins that base group (`groups[].alsoIn`, Issue `Also when hovered.`).
- Reference worse (not counted): a responsive row where only the Reference overflows, scrolls or is
  clipped at a width where the Target fits is not actionable; it keeps the `Reference larger: ...`
  Action and is listed under `## Reference worse (not counted)` (`groups[].referenceWorse`).
- Layout-table cells (implicit-role `cell` of a header-less table nested in a cell or holding a nested
  table, e.g. WebForms/jqGrid pagers) are left out of element matching; the controls inside stay compared
  (`runs/Module<X>/match_<state>.json excludedLayoutCells`). A layout cell with text of its own (pager
  caption, form label) is compared by that text; not found on the other side gives a LOW, not counted
  row `(layout text not found on Target)` (`layoutTextCells`). Module<X>_CSS_Diff.md shows both counts.
- Empty tables show one `None found.` row (never a bare `(none)`).
- Module-result summary: `Target 13/13 steps passed (55/55 assertions), module FAIL (styling/layout open)`;
  the step count never reads as failed steps. Counted `Reference larger` groups are named in the
  `What this means` line (`N of them are old-page defects to accept or confirm, not to copy`) and the
  `What to do` line tells the reader to confirm/accept them instead of changing the new page.

- Actionable counts (summary.json `actionableCssDiffs`, status.json, chat `CSS groups`) are groups owned
  by the module (first module in plan order the group was seen in); other modules' reports show
  `see page-level group G3 (owned by Module A)`. Raw-row counts are informational (`actionableCssRows`);
  a module with actionable raw rows never passes.
- Group severity = highest member severity (a HIGH row never sits in a LOW group).
- Chat module-result and final views: top 15 actionable groups (severity, then element count) plus
  one line `N more in reports/CSS_Groups.md`. FinalReport.md (and its PDF/DOCX) lists every group, never
  the raw rows.

### Geometry rows (layout.*)

Geometry diffs use the same table. Property is a `layout.*` metric derived from the css-map `role`
elements: `layout.height` (grid), `layout.rowHeight` (first data row), `layout.headerHeight`,
`layout.gapToPager` (last visible row bottom to pager top), `layout.gapToGrid` (filter panel to grid).

```markdown
| Grid pager [page_load] | layout.gapToPager | 2px | 300px | HIGH | Fix Target layout: layout.gapToPager 300px vs Reference 2px (diff +298px, 14900%) |
```

- Within tolerance (|diff| ≤ 4px or ≤ 10%, appsettings `VisualChecks.Geometry`): no row.
- Outside tolerance: **MEDIUM**; **HIGH** when the diff is > 40px or > 50%. Never LOW, so every geometry
  row is actionable unless the element accepts it (`"accepted": { "layout.rowHeight": "<reason>" }`).
- Direction: Target larger → Action `Fix Target layout: ...`. Reference larger → Action
  `Reference larger: ... Confirm on the Reference page ...`: still counted, but the Target is never
  given extra empty space or height to match; the user accepts it or treats it as a Reference issue.
- Unmeasured: a role element whose Reference selector matched nothing gives a counted MEDIUM row
  `(unmeasured)` (Reference `missing`); a pager/filter element without a `row`/`grid` element in the
  state gives `(unmeasured: needs role <r>)`. A metric that cannot be measured never passes silently.

### Automatic inventory rows

Same table, from the element inventories of both sides (`summary.json cssDiffs[].layer`; method in
`css-comparison-methodology.md`). Element = css-map name or `<role> '<accessible name>'`.

| Layer | Property | Severity |
|-------|----------|----------|
| match | `(missing on Target)` | HIGH |
| match | `(extra on Target)` | LOW (not counted), MEDIUM if interactive |
| match | `(layout text not found on Target)`, `(layout text only on Target)` | LOW (not counted) |
| match | `text.name`, `text.label`, `text.placeholder` | MEDIUM (LOW: case/punctuation only) |
| style | normalized computed style of an auto pair | as mapped properties |
| state | `hover.*`, `focus.*`, `disabled.*` | HIGH for color/background, else MEDIUM |
| layout | `layout.order`, `layout.overflow`, `layout.lines`, `layout.overlap`, `layout.hidden` | HIGH |
| layout | `layout.align`, `layout.labelPosition`, `layout.spacing` | MEDIUM |
| responsive | `responsive.<width>.overflow`, `.lines`, `.hidden`; element `(page)` for page scroll | HIGH |

- Accepted rows (css-map `accepted`, or the stack profile: Action column `accepted by profile
  <name>: <reason>`) are listed under Accepted and never counted. css-map acceptance wins over the profile.
- px rows where the Reference is larger keep the `Reference larger: ...` Action (never pad the Target).
- Chat and final views show the property in plain English (`reading order`, `background-color on
  hover`, `overflows at 768px width`); FinalReport.md keeps the raw name in brackets for the audit.

## Content Sanity Checks

Every step snapshot on BOTH sides is scanned (visible `innerText`) for leaked server/template syntax
(`<%@`, `<%`, `%>`, `@code`, `@page`, `{{`, `}}`; standalone `undefined`, `NaN`, `[object Object]`),
and browser console errors / unhandled page errors are recorded. Token lists: appsettings `VisualChecks`.
At every CSS state the element inventory adds broken images, empty headings/sections and accessibility
gaps; failed network requests (HTTP ≥ 400 or network failure, same origin or asset) are recorded per
step (appsettings `VisualChecks.PageHealth`).

| Side | Category | Severity | Counted |
|------|----------|----------|---------|
| Target | FUNCTIONAL GAP, kind `app`, field `page.leakedSyntax` | HIGH | yes (fails Target parity) |
| Target | FUNCTIONAL GAP, kind `app`, field `page.brokenImage` / `page.failedRequest` | HIGH | yes |
| Target | FUNCTIONAL GAP, kind `app`, field `page.consoleError` / `page.pageError` | MEDIUM | yes |
| Target | FUNCTIONAL GAP, kind `app`, field `page.emptySection` / `page.a11y` | MEDIUM | yes |
| Reference | **Reference defect** (baseline issue, id `<X>-REF<n>`) | HIGH (syntax, broken image, failed request) / MEDIUM (errors, empty section, a11y) | no: listed in the parity report, the module-result render and FinalReport.md `Reference Issues`; never fails Target parity |

## Final Report Sections (Phase 6)

In the workflow FinalReport.md is generated by lifecycle.ps1 -Action report (no hand-written content).

1. **Executive Summary** — Overall result, metrics
2. **Module Results** — Per-module pass/fail table
3. **Functional Gaps** — All gaps across modules
4. **CSS Comparison** — All diffs resolved
5. **Bug Fixes** — Issues found and fixed
6. **Manual Tests** — NOT_TESTED items
7. **Limitations** — Known constraints
8. **Reference Issues** — Reference defects found on the baseline (not counted in Target parity)
