# Phase 3: Cross-System Comparison & Reports

Reference: `#phase-3-comparison.md`
Used by: the runner (`lifecycle.ps1`) after each module's Target run, and the
`comparison-reporter` agent for the final report.

---

## Purpose

Comparison reports for every module: data parity, CSS differences, performance and manual
test instructions. **They are generated by the runner** (`run-page`, `rerun-target`,
`report`) from `runs/Module<X>/{Reference,Target}/results.json`, the CSS captures and
`state-map/css-map.json`. Nobody writes or presents them by hand per module.

| Report | File |
|--------|------|
| Data parity + Step Report + Functional Gaps + Summary | `reports/Module<X>_Parity.md` |
| CSS diff | `reports/Module<X>_CSS_Diff.md` |
| Performance (Reference ms vs Target ms per step) | `reports/Module<X>_Performance.md` |
| Manual tests (NOT_TESTED items) | `reports/Module<X>_ManualTests.md` |
| Machine summary (findings with kind, CSS diffs) | `runs/Module<X>/summary.json` |
| All modules (final report, gate 2) | `reports/FinalReport.md` (generated by `-Action report`) |
| Chat view per module | `chat/NN-module-result-<X>.md` (rendered by the runner, relayed as CHAT-RENDER) |

---

## Step 3.1: Data Parity (per module)

Findings are keyed and deduped on `(step, field)`. Assertions pair between Reference and
Target on `(step, field, type)`. Each finding gets exactly one **kind**, first match wins:

| Order | Kind | Rule | Counted |
|---|---|---|---|
| 1 | `test-coverage` (step) | A Reference step has no Target step with the same name | yes |
| 2 | `test-selector` | Target step aborted / timed out, NAV FAIL, or an existing Target capture is empty or `__missing` | yes |
| 3 | `test-expectation` | Paired EQUALS/CONTAINS/BOOL whose expected constants differ | yes |
| 4 | `app` | Failed Target assertion; paired CHANGES/STAYS SAME whose actual differs from Reference; captured-value mismatch | yes |
| 5 | `test-coverage` (assertion) | Only Reference-only assertions and/or missing captures on a step Target has | yes, MEDIUM |
| — | `unmatched-target-assertion` | Target-only assertion or capture | no, LOW (listed) |

Every finding carries `missingAssertions` and `missingCaptures`, so a dropped Reference
assertion or capture always blocks `fixLoop.clean`.

**Severity** (functional gaps, `#reporting-standards.md`): HIGH = different data/behavior,
MEDIUM = different messaging, LOW = formatting only. Row-5 findings are MEDIUM.

---

## Step 3.2: CSS Diff (per module)

Elements come from `state-map/css-map.json` (Reference selector ↔ Target selector per
state). Severity per property from the map, else the defaults (HIGH visually noticeable,
MEDIUM size/spacing, LOW no visual impact).

`actionableCssDiffs` = mapped HIGH/MEDIUM diffs that are not `accepted`, plus planned CSS
states missing on Target, plus one "unmapped" diff per planned state when css-map.json is
missing.

Ignore rules (not real differences):
- ±1px on dimensions
- rgb vs hex (same color)
- Font rendering platform differences
- flex vs inline-block when visual output identical

## Step 3.3: Manual Test Instructions

For every NOT_TESTED item (from `plan.json notTested`):

```markdown
# Module {X} — Manual Tests

## Test 1: [Description]
**Why not automated:** [reason]
**Pre-conditions:** [setup]
**Steps:**
1. Navigate to [URL]
2. [action]
3. [action]
**Expected:** [what to verify]
**Pass criteria:** [how to know it passed]
```

---

## Step 3.4: Consolidated Module Report

`reports/Module<X>_Parity.md` combines the functional and CSS summary per module.

---

## Step 3.5: Presentation (moved to the final report)

There is no per-module presentation gate. Presenting a module report is satisfied by writing
it plus the `module-result` chat render, which the run step relays into the chat as soon as
the module finishes (Reference and Target step reports, performance, functional gaps, CSS
diffs). All module reports are presented once more in `reports/FinalReport.md` at gate 2
(final report sign-off). Findings go to Phase 4 (auto-fix) automatically.
