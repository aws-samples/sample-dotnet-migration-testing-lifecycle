# Test Framework — Reusable Playwright Infrastructure

This directory contains the **application-agnostic** test infrastructure (a shared Harness
library), one small NUnit project per test module, the report/render tool, and the runner
`lifecycle.ps1`. Only `lifecycle.ps1` calls `dotnet`; agents and users call its actions.

## Layout

```
.kiro/test-project/
  lifecycle.ps1, appsettings.test.json, auth-state.json (generated, git-ignored), README.md, Specs/
  Harness/                         shared class library (built once, mutex-protected)
    MigrationTests.Harness.csproj
    ModuleTestRunner.cs  TestBase.cs  GlobalSetup.cs  HarnessPaths.cs
    Helpers/*.cs                   CssCompareHelper, ElementInventory, PageHealth, AuthHelper, ModuleReportGenerator, AppPageHelper, ...
    Models/*.cs                    TestSettings, TestCaseResult
    Reporting/*.cs                 automatic CSS diff (ElementMatcher, AutoCssComparer, CssGrouper, ...), chat
                                   renders, FinalReport and the PDF/DOCX documents
    Shared/ModuleSetUpFixture.cs   compiled into each module project, not into Harness
  Harness.Tests/                   NUnit unit tests (headless; ElementInventoryBrowserTests uses headless
                                   Chromium, LoginSetupTest is the interactive login helper, see below)
    MigrationTests.Harness.Tests.csproj
    *Tests.cs  LoginSetupTest.cs  Fixtures/PayorListMini/
  Reports/                         console tool: module reports, FinalReport.md, chat renders
    MigrationTests.Reports.csproj  Program.cs
  profiles/                        stack profiles (generic.json + one per Reference/Target stack pair), see below
  Modules/                         one NUnit + Playwright project per module
    {Page}.Mod{X}/{Page}.Mod{X}.csproj        (created by -Action build-module when missing)
    {Page}.Mod{X}/Reference{Page}Module{X}_v2.cs  (Reference test, method Reference{Page}_Mod{X})
    {Page}.Mod{X}/{Page}Module{X}_v2.cs           (Target test, method {Page}_Mod{X})
```

Bundled modules: `PayorList.ModA` .. `PayorList.ModD` (generated by the workflow for the
sample; delete them for another app). Namespaces are unchanged
(`MigrationTests.Playwright`, `MigrationTests.Playwright.Tests`, `MigrationTests.Reporting`).

Run the Harness unit tests from the repo root:

```powershell
dotnet test .kiro/test-project/Harness.Tests --filter "FullyQualifiedName!~LoginSetupTest"
```

The filter leaves out `LoginSetupTest`. It opens a headed browser at `BaseUrl` to save a
sign-in, so it fails when the apps are not running.

Each module project has its own `bin/` and `obj/`, and each run writes to
`.kiro/app-testing/<Page>/runs/Module<X>/<System>/`, so modules build and run in parallel
without sharing files.

## Runner: `lifecycle.ps1`

`lifecycle.ps1` is the only process that runs anything (environment check, app start, build,
tests, reports, chat renders) and the single writer of `.kiro/app-testing/<Page>/status.json`,
`timings.json`, `PROGRESS.md` and `chat/`. Run it from the repo root (Windows PowerShell 5.1;
PowerShell 7 should work but is untested); keep `PROGRESS.md` open in an editor tab to watch a run.

```powershell
.\.kiro\test-project\lifecycle.ps1 -Action doctor                                     # environment checklist
.\.kiro\test-project\lifecycle.ps1 -Action build-module -Page PayorList -Module A     # build one module
.\.kiro\test-project\lifecycle.ps1 -Action run-page -Page PayorList -Modules A,B,C,D  # run modules (foreground)
.\.kiro\test-project\lifecycle.ps1 -Action render -Page PayorList -View plan          # chat view as markdown
.\.kiro\test-project\lifecycle.ps1 -Action status -Page PayorList                     # short summary
```

### Actions

| Action | What it does |
|--------|--------------|
| `doctor [-Page P]` | Prints `[PASS]/[FAIL]/[WARN] <check> - <detail>` per check (11 checks); every FAIL ends with `Fix: ...`. Required: dotnet SDK majors (from the Harness, every `Modules/*/*.csproj` and the app projects), ExecutionPolicy (the policy a new shell gets must allow local scripts; fix `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`), Playwright `chromium-<rev>` + `chromium_headless_shell-<rev>`, settings, stack profile (the `StackProfile` file and its `extends` chain exist and parse; not set = WARN), ports, repo folder is the current directory (Kiro workspace), zero-prompt rules installed. Advisory: source paths (`ReferenceSourcePath` / `TargetSourcePath` set and present), git, Kiro workflows enabled. Writes `doctor-result.json`; with `-Page` also the `## Environment` section of PROGRESS.md. Runs automatically as step 0 of `run-page`, `rerun-target` and `preflight`. |
| `build-module -Page P -Module X` | Creates `Modules/P.ModX/P.ModX.csproj` when missing, builds the Harness once (mutex `Local\MigrationTests.HarnessBuild`, skipped when its stamp is fresh), then only this module. Writes `runs/ModuleX/build.json`. Prints `[build-module] X PASS 3.1s (Ref 13 steps/54 assertion calls, Tgt 13/38, rev 1)` or `[build-module] X FAIL ... log=logs/build-X.log` plus the first 5 `error CS` lines. No page lock, so several authors can build at once. |
| `run-page -Page P [-Modules A,B] [-MaxParallel n] [-Detach] [-Screenshots all\|failed\|none]` | Doctor -> session rule -> start any app in `Apps` that is down (or restart a stale Target) -> build Reports/Harness if stale and all module projects in parallel -> Playwright check/auto-install -> verify the test methods exist -> schedule: all `read-only` modules in parallel (Reference and Target together, at most `-MaxParallel` modules, default 4), then each `mutating` module alone with a data-service restart after its Reference and after its Target run -> reports and a `live-status` chat render each time a module finishes -> after all modules, one `module-result` render per module in plan order -> `run-summary` render. Without `-Modules`: plan order. Without `-Detach` it runs in the foreground (manual use). With `-Detach` it starts the run in a background `powershell.exe`, prints `[run-page] detached runner pid=<pid> runId=<runId>; console log ...` and returns in about 2 s (workflow use, paired with `wait`). |
| `wait -Page P [-TimeoutSec 90]` | Waits up to `-TimeoutSec` (30..1800) for the detached run, prints every new chat render as `CHAT-RENDER <abs path>` + summary line, then exactly one last line: `[wait] run=running`, `[wait] run=running (no new results in <n>s)`, `[wait] run=finished exit=<code>[ <message>]` or `[wait] run=crashed exit=1 (...)`. Its exit code is the run's code once finished. Call it again while it says `run=running`. |
| `render -Page P -View <view> [-Module X]` | Renders a chat view to `chat/NN-<view>[-X].md` and prints `CHAT-RENDER <abs path>` and a one-line summary. Views: `plan`, `tests-authored`, `live-status`, `module-result` (needs `-Module`), `run-summary`, `fix-round`, `final`. Every report section is one table (never split). Only the plan view has several files: `NN-plan.md` (overview) and `NN-plan-<X>.md` (one per module); it prints one `CHAT-RENDER` line per file, in relay order. |
| `rerun-target -Page P -Modules A,B` | Target-only rerun after a fix (Reference must have a passing baseline); `-Module X` is still accepted and merged. Restarts the Target app only when down or stale; prints `target-restarted=true\|false`; keeps `results.prev.json`; regenerates the reports; prints `[fix-round] round r Module X: findings a -> b, CSS c -> d`. |
| `fix-round -Page P [-Source loop\|final-gate]` | Opens a fix round (prints `round=<n>`), or `round=<n> budget-exhausted` after 2 loop rounds. `final-gate` is never budget-limited. |
| `gate -Page P -Gate plan_signoff\|final_signoff\|baseline_failed -State pending\|confirmed [-ResponseFile f] [-ReportPath p]` | Records a human gate (and the gate wait in the lifecycle timings). |
| `progress -Page P [-Phase 0..4] -Message 'text'` | Sets PROGRESS `Now:`; `'HARNESS-ERROR <X>: <reason>'` marks a module. `-Phase k` marks the start of phase k (0 Plan, 1 Author tests, 2 Run Reference + Target, 3 Fix, 4 Report); console `phase <k+1> (<name>) marked`. |
| `report -Page P` | Regenerates every module's reports and writes `reports/FinalReport.md`, `FinalReport.pdf`, `FinalReport.docx` (same sections) and `TestCaseResults.pdf` / `.docx` (per module and step: plain-English description, Reference and Target status, expected vs actual, Reference and Target screenshots side by side) with the Reports tool (`[report] <file> (<bytes> bytes)` per document, `[report] reports/FinalReport.md written (N modules)`). No hand-written content; about 3 s for PayorList. |
| `reset -Page P` | Archives the page state to `previous-run/<timestamp>/` and writes a fresh status.json. |
| `status [-Page P]` | Read-only summary incl. the phase line (without `-Page`: URLs plus `[OK]/[DOWN]` per `Apps[]` entry). |
| `preflight`, `build`, `run-module`, `stop` | Legacy actions, still available (`preflight` = doctor + app start + sign-in when `Auth.LoginUrl` is set; `build` builds Harness, Reports and every module). |

### Parameters

| Parameter | Values | Used by |
|-----------|--------|---------|
| `-Page` | page name, e.g. `PayorList` | every page action |
| `-Module` | one module id | `build-module`, `render -View module-result`, `rerun-target` |
| `-Modules` | `A,B,C` | `run-page`, `rerun-target` |
| `-View` | `plan`, `tests-authored`, `live-status`, `module-result`, `run-summary`, `fix-round`, `final` | `render` |
| `-Screenshots` | `all` (default), `failed`, `none` | `run-page`, `rerun-target` |
| `-MaxParallel` | 1..8 (default 4) | `run-page`, `rerun-target` |
| `-Detach` | switch | `run-page` |
| `-TimeoutSec` | 30..1800 (default 90) | `wait` |
| `-Phase` | 0..4 (default -1 = none) | `progress` |
| `-Gate`, `-State`, `-ResponseFile`, `-ReportPath` | see `gate` | `gate` |
| `-Message` | single-quoted, one line, at most 200 chars, no `$` or backtick | `progress` |
| `-Source` | `loop`, `final-gate` | `fix-round` |

### Exit codes

| Code | Meaning |
|------|---------|
| 0 | Ran (findings allowed) |
| 1 | Harness error only: bad arguments, build failure, missing test, lock held, report/render failure, status.json write failure |
| 2 | Reference baseline failed (`Reference baseline failed for Module(s) A, C: ...`) |
| 3 | Environment/preflight failure (nothing ran) |

A failing or timed-out test is never exit 1 by itself: the verdict comes from
`runs/Module<X>/<System>/results.json`. When several modules run, the message names each
affected module (e.g. `Module(s) B: test not found: PayorList_ModB`).

Apps are configured in `appsettings.test.json` -> `Apps` (`name`, `project` relative to this
folder, `healthUrl`, `healthAccept` = `status200` (default) or `anyResponse` for SOAP/WCF
endpoints that answer GET with 500, `isTarget`, `resetData` = `true` on the app whose
restart resets the test data, e.g. the in-memory `service`). Logs go to
`.kiro/app-testing/<Page>/logs/`. State file contract: `Specs/status.README.md`.

Source folders: `ReferenceSourcePath` and `TargetSourcePath` in `appsettings.test.json`
(repo-root relative, e.g. `sample/PayorContracts.Legacy` and `sample/PayorContracts.Web`). `progress -Phase 0`
copies them into `status.json` `paths.reference` / `paths.target`, where the agents read
them: the Reference source is never edited, Target fixes go only under `paths.target`.
Doctor prints both.

### Run history

Each `test-page` run gets a run id `run-YYYYMMDD-HHMMSS` (`status.json` `session.id`) and
never reuses an earlier run's results. After every run action, gate and chat render, the
runner copies that run's outputs to
`.kiro/app-testing/<Page>/history/<runId>/` (`reports/`, `chat/`, `runs/`, `timings.json`,
`fixes.json`, a `status.json` snapshot) and updates `history/index.json` and
`history/README.md`. Top-level `reports/` and `chat/` are always the latest run. To prune,
delete old `history/<runId>/` folders and their entries in `history/index.json`.

### Screenshots (test case results document)

In lifecycle mode `ModuleTestRunner.ExecuteStep` saves a JPEG (quality 70, viewport size, 5 s
timeout, never fails the test) after each step's checks and before the next action, to
`.kiro/app-testing/<Page>/runs/Module<X>/<System>/screenshots/<step>.jpg`, and records the
path in `results.json` `steps[].screenshot`. `report` puts the Reference and Target shots of
each step side by side in `reports/TestCaseResults.pdf` / `.docx`. Steps recorded without
`ExecuteStep` (for example a manual `StepPass("NAV", ...)`) have no page and no screenshot.

Policy: `-Screenshots all|failed|none` on `run-page` / `rerun-target` (env
`LIFECYCLE_SCREENSHOTS` for the test process). `failed` captures failed steps, the first
step and the module's last planned step (`LIFECYCLE_LAST_STEP`). The default is `all`
(`$DefaultScreenshots` in `lifecycle.ps1`): measured on PayorList before the visual checks
were added (A-D, 68 screenshots, about 5.2 MB), the Run phase took 02:29 with `all` against 147 s without screenshots
(+1.4%, below the 10% limit). If a page's Run phase grows by more than about 10%, pass
`-Screenshots failed` or set `$DefaultScreenshots = 'failed'`.

### Measured (PayorList, 4 modules)

On the dev box that also hosts the three sample apps, before the visual checks were added,
`run-page` for A, B, C, D took 157.4 / 165.1 / 173.6 s wall in three parallel runs and 222.3 s
with `-MaxParallel 1`. With the visual checks the latest run took 174.4 s (see
[docs/RUN-TESTING-LIFECYCLE.md](../../docs/RUN-TESTING-LIFECYCLE.md#7-expected-duration-bundled-sample)). Pass counts were identical in all runs. `build-module` takes about 3 s per
module once the Harness is built.

## How to Use

1. Keep the Harness as is; add your app's interactions in `Harness/Helpers/AppPageHelper.cs`.
2. Point `appsettings.test.json` at your apps (`BaseUrl`, `ReferenceBaseUrl`, `Apps`).
3. Write one module per user workflow under `Modules/{Page}.Mod{X}/` (the workflow's author
   step does this), then `-Action build-module -Page {Page} -Module {X}`.
4. Run with `-Action run-page -Page {Page}`.

## Visual comparison settings (`VisualChecks` in appsettings.test.json)

Besides the css-map rows, every CSS state gets an automatic element inventory on both sides
(`runs/Module<X>/<System>/css/inventory_<state>.json`); the report step pairs the elements and
writes `runs/Module<X>/match_<state>.json`. Method: `.kiro/steering/css-comparison-methodology.md`.

| Setting | Default | Meaning |
|---------|---------|---------|
| `Inventory.Enabled` / `MaxRowsPerGrid` / `MaxElements` / `MinMatchScore` | true / 3 / 300 / 0.6 | discovery on/off, grid rows compared, element cap, pairing threshold |
| `InteractiveStates.Enabled` / `States` / `MaxElements` | true / `["page_load"]` / 12 | hover/focus/disabled styles of the first N interactive elements (Chromium: pseudo-classes forced via CDP, no mouse/focus/blur events reach the app; other browsers: real hover, focus skipped on text inputs/selects) |
| `Responsive.Enabled` / `States` / `Widths` | true / `["page_load"]` / `[1366, 768]` | re-inventory at each width (viewport restored afterwards) |
| `IgnoreProperties` | `["cursor"]` | never compared on non-interactive elements |
| `PageHealth.BrokenImages` / `FailedRequests` / `EmptySections` / `Accessibility` | all true | extra health checks (Target = findings, Reference = Reference defects; requests the browser aborted itself, e.g. `net::ERR_ABORTED` on postback/navigation, are ignored) |
| `Layout.SpacingMinDiffPx` / `AlignTolerancePx` | 4 / 2 | spacing row threshold (plus the Geometry tolerance), aligned-edge tolerance |
| `StackProfile` (top level) | `""` = generic only (the sample sets `webforms-jqgrid__blazor-mudblazor`) | `profiles/<name>.json` with the stack pair's role equivalences, selector hints and accepted-by-default differences |
| `Severity.FontSizeLowPx` / `BoxLowPx` / `TextMetricLowPx` | 1 / 1 / 1 | a font-size / border-radius, padding*, margin*, border-*-width / letter-spacing, line-height difference up to this many px is LOW (not actionable), above it MEDIUM |
| `Severity.DeltaELow` / `DeltaEHigh` | 3 / 10 | CIEDE2000 color difference: below DeltaELow LOW, up to DeltaEHigh MEDIUM, above it HIGH on text/background of interactive or `PrimaryRoles` elements (else MEDIUM) |
| `Severity.ContrastMin` | 4.5 | WCAG AA: Target text contrast below it where the Reference passes is HIGH (wins over deltaE) |
| `Severity.LowFontWeightPairs` / `PrimaryRoles` | `[["500","600"]]` / heading, columnheader, banner, navigation, tab | font-weight pairs that are LOW; roles treated as primary for the color rule |
| `Groups.ChatTop` / `ExampleElements` | 15 / 3 | actionable CSS groups shown in the chat module-result and final views; example labels per group |

Severity rules apply only to style/state/mapped rows (match, layout, responsive and geometry rows
keep their severity; a severity written per property in css-map.json wins). Unparsable values
(`normal`, `%`, `auto`) keep their severity. After all modules' rows are produced the report groups
them per page (`CssGrouper`): `runs/css_groups.json`, `reports/CSS_Groups.md` and the audit
`runs/css_rows_all.json` / `.md` (every raw row with its group id and severity rule). summary.json
`actionableCssDiffs` = actionable groups owned by the module (first in plan order),
`actionableCssRows` = raw rows; `cssGroupsSeen` / `cssGroupsOwned` list the group ids.

css_groups.json `groups[]` also carries: `issue` (one plain-English sentence from `IssueText`
templates, the Issue column of every CSS table and the fixer's task title), `alsoIn` (hover / focus /
disabled states folded into a base-state group because their values are the same), `referenceWorse`
(responsive rows where only the Reference overflows/clips: listed under "Reference worse (not
counted)", never actionable) and `inAllStates` (Seen in shows `all N states`). Border sides with
identical values are one group with property `border` / `border (top, bottom)`. Grid cell rows carry
`columns` (column header text found by geometry) in summary.json `cssDiffs[]`. Layout-table cells
(header-less tables nested in a cell or holding a nested table, e.g. jqGrid pagers) are left out of
matching and listed per state in `runs/Module<X>/match_<state>.json` `excludedLayoutCells`; those with
text of their own (pager caption, form label) are compared by that text instead (`layoutTextCells`;
not found = LOW, not counted row `(layout text not found on Target)`).

The inventory logs its time per state (`[inventory] page_load 120 elements, 900 ms` in the test log).
To save time on a large page lower `InteractiveStates.MaxElements` / `Inventory.MaxElements`, or
set `Responsive.Enabled` false.

## Stack profiles (`profiles/`)

`generic.json` holds stack-neutral equivalences and is always applied last. A pair profile (e.g.
`webforms-jqgrid__blazor-mudblazor.json`, naming `<reference-stack>__<target-stack>`) declares
`"extends": "generic"` and adds `roleEquivalences`, `selectorHints` (widget part selectors per side
for the planner), `accepted` (property exact or `prefix*`, optional `role`, `element` substring,
`reference`/`target` value regexes, mandatory `reason`), `ignoreProperties` and `ignoreRoles`.
Acceptance order: per-page css-map `accepted` wins, then the profile (report text
`accepted by profile <name>: <reason>`). `lifecycle.ps1 -Action doctor` checks that the selected
profile and its `extends` chain exist and parse. See also the user guide "Adding a stack profile".

## Key Design Decisions

- **NUnit** as test framework (single `[Test]` per module for sequential flow)
- **One project per module** so builds and runs never collide; the Harness is built once
- **Single browser context** per test process (auth state preserved)
- **Three test modes** controlled by `APP_TEST_MODE` environment variable:
  - (empty): Normal mode — headed browser, screenshots captured
  - `validate`: Fast mode — headless; findings cause test failure
  - `report`: Documentation mode — headed with SlowMo, captures everything

  The runner always sets `validate` (headless). Lifecycle screenshots are still taken (see
  Screenshots above) and the verdict comes from `results.json`. Empty and `report` are for a
  manual `dotnet test` only.
- **ModuleTestRunner** is the core engine — handles assertions, timing, HTML diff, CSS capture, and report generation automatically
